## Context

盤點雲端正式站與代碼庫落差時發現的 4 個獨立修復項目，共通點是：代碼多半已經寫好，缺的是「真的接上」或「安全合併」，不是從零開發。

## Goals / Non-Goals

**Goals:**

- 讓 SR-01（role-based-workspace-navigation）的核心承諾真正落地到畫面上
- 頭像上傳失敗時使用者/工程師都能知道原因
- 客服按鈕不再擋畫面
- 電子報自動寄送引擎安全合併進 main，不破壞既有退訂/同意邏輯

**Non-Goals:**

- 不在這份新增任何新功能（新功能在 `course-platform-feature-parity`）
- 不重構 NavBar 以外的共用元件

## Decisions

### 電子報合併採「技術實作用新的，行為邏輯要核對」原則

`schema.prisma`、`mail/provider/*` 這類純技術實作，main 版本已確認更完整，直接採用；但涉及使用者同意/退訂這類會影響真人權益的邏輯，即使要多花時間，也要核對兩邊語意一致才能合併，無法確定就停下回報。

### NavBar 修復需要新增之前完全沒有的測試案例

之前的「30/31 完成」是不準確的，因為沒有測到「總管理員進 App 顯示對應管理員身份」這個 SR-01 真正要解決的案例。這次要把這個案例補上，不能只是接上程式碼就算數。

## Implementation Contract

**Behavior：**

- 總管理員進入課程 App，選單顯示「課程管理員」身份與對應設定，不再是單純「總管理員」全域標籤
- 頭像上傳失敗時畫面顯示具體錯誤，環境齊全時上傳成功
- 客服按鈕可收合，收合狀態能被記住
- main 上有完整可運作的電子報自動寄送引擎

**失敗模式：**

- 電子報合併若發現行為衝突無法安全判斷，停止該部分自動合併，回報而非猜測
- 頭像上傳若本機無可用 S3 測試環境，明確標記「受限於環境，無法端到端驗證」，不可假裝驗證過

**驗收標準：**

- 各 spec 檔案的 Scenario 逐一對應自動化測試或手動驗證紀錄
- `pnpm build` 通過
- 電子報合併後跑一次既有退訂/同意相關測試，確保沒有變紅

**範圍邊界：**

- 只處理這 4 項，不擴大到其他發現的問題

## Risks / Trade-offs

- 電子報合併是這份風險最高的項目，涉及使用者同意/退訂的合規邏輯，寧可停下回報也不要用猜的合併
- NavBar 改動涉及核心選單邏輯，需要完整跑過既有 `NavBar.test.tsx` 確保沒有破壞舊行為
- 頭像上傳的 S3 環境變數如果連正式站都缺，這條會變成需要 Fish 提供憑證才能完整驗證
