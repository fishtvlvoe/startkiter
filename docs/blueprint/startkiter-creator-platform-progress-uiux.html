01 · 先看懂產品邊界

「我們的營運網站」跟「客戶買回去的程式包」是兩個產品

白話說：StartKiter 是我們自己用來管理課程、商品、客戶、行銷和直播的工作室；CodePackage 是交到買家手上的一份程式原始碼。買家可以用它另外做自己的 SaaS，自己的會員、收費和部署由買家那套系統負責。

A · 我們的 StartKiter 平台

我們在這裡營運生意

  • 建課程、組合包、單堂課、程式包商品
  • 管理名單、優惠、付款、訂閱與交付
  • 未來加 CRM、Email、自動化、網站、直播、報表
B · 買家取得的 CodePackage

買家拿到一份獨立程式碼

  • 可以做自己的 SaaS 或會員網站
  • 買家的登入、客戶資料、訂閱、主機是買家自己的
  • Codex Desktop／Claude Desktop Code 模式可照操作手冊或 Skill 使用
C · 不能混成一件事

買一門課，不等於全站都能看

  • 單堂課只開那一堂
  • Bundle 開組合包裡的課
  • CodePackage 可以自己單賣，也可由 Offer 決定是否附送／訂閱期間可用

核心做法：內容是什麼、賣什麼、買家付了什麼、買家因此能看／能下載什麼，分開記錄。以後加訂閱、Bundle、獨立程式包，才不會把課程權限和整站登入混在一起。

03 · 一條生意從建立到交付

先做完一條完整路徑，再複製這個做法加下一種功能

不要一次做完整個 Systeme.io。先確保一種商品從後台設定、客人付款，到權限和商品交付都對，再用同一套商品／Offer／權限規則擴充。

組合包不是「全站通行證」；付款通知只依訂單當下記錄的商品授權對應內容。

每張 SR 都用同一套開發流程

先定義完成樣子

列清楚誰能做什麼、做完畫面與資料變什麼。

先寫會失敗的測試

先證明舊行為／新需求的界線，避免只憑感覺改。

只改這張 SR 的範圍

沿用現有模組；必要時加遷移，不重做已存在的地基。

把主要路徑走一遍

測試、API、桌機和手機 UI；金流／Email 要走相應驗收。

回歸、回滾，再封存

檢查沒弄壞旁邊功能，留證據；過門檻後才交付。

如果某一關失敗：先回到那張 SR 修正並重跑該關，不把未通過的功能接到下一張 SR 上。
