規則對焦版
SR architecture focus · 2026.09.21

讓每張 SR 都接在同一條 產品骨架 上

這不是單純換版面。這張圖先把產品邊界、獨立 App 模組、資料與權限、角色工作區、設定入口、開發 Skill、測試、部署與驗收放回同一張地圖。

本次固定規則
管理者設定只對管理者出現

一般使用者只看到自己的設定、幫助、升級與登出。App 管理員與總管理員才多一個管理者設定入口，兩套選單不再混在一起。

01 / 邊界 每個功能都是獨立 module

模組自帶路由、權限、選單、翻譯、SVG icon 與測試。

02 / 組合 平台外殼只負責組合

Shell 不重寫每個功能的畫面，只讀 module contract。

03 / 證據 完成不是 build 綠燈

要通過測試、部署後瀏覽器、角色、語系、主題與手機驗收。

總架構

一張 SR 從決策走到可賣產品

點擊每一層，查看它負責什麼、不能越界什麼。

模組骨架

功能獨立，平台統一接線

學生新增 App 模組時，知道自己要負責哪一段，也知道不能直接碰哪一段。

每個 module 自己帶的東西

  • 業務與資料自己的 domain、schema、server action 或 API 邊界
  • 路由與權限route、capability、route guard，不靠 UI 隱藏保護
  • 選單宣告workspace、一級 parent、子級 children、排序與 active route
  • 可見內容translation namespace、SVG icon light/dark 版本、semantic token
  • 自己的證據unit、component、locale、browser acceptance test

平台外殼統一負責的東西

Module registry收集並檢查 module manifestregistry
Workspace resolver一次只選出一個角色工作區resolver
Shell composer產生一級與子級選單，不重複渲染shell
Acceptance gates把規則變成測試與部署後證據gates

建議 SR 順序

先固定骨架，再讓功能一個一個掛上去

每一張 SR 都有自己的完成條件，但不能跳過共同骨架。

現在對焦SR-01 邊界與導航契約

固定 workspace、module manifest、一級／子級選單與「只出現一套」的規則。

依賴 SR-01SR-02 開發 Skill 與模組接線

學生安裝後知道怎麼加功能，Skill 引導，型別與測試硬性把關。

依賴 SR-02SR-03 帳號與偏好設定

設定、主題、語系集中在帳號區，管理者設定只對管理者出現。

依賴前面三張SR-04 真正 App 模組

課程、內容、測驗、社群等 App 各自獨立，透過 contract 掛回平台。

每張都要SR-05 部署與產品證據

測試、ego-browser、手機與桌面、語系、主題、錯誤狀態與回滾證據。

完成閘門

每張 SR 都要留下這些證據

沒有這些證據，只能說完成規劃，不能說功能完成。

範圍清楚

有目標、非目標、依賴與 rollback，不把未決議題藏在程式碼裡。

模組有關聯

route、permission、menu、i18n、SVG 與資料流可以從 manifest 找到。

角色不越界

每個 App 的使用者與該 App 管理員各看自己的工作區，平台層只有總管理員。

自動檢查

unit、component、locale、token 與 duplicate route 檢查通過。

真實瀏覽器

部署後以 ego-browser 驗證桌面、手機、語系、主題與每個可見入口。

可回報

commit、branch、驗證輸出與尚未驗證的部分分開說清楚。

邊界管理

這張對焦頁不把所有事情混成一張 SR

先把相鄰工作標出來，下一張 SR 才不會無意間改到不該改的地方。

本架構會處理

  • 角色工作區與一級／子級選單
  • module manifest、Skill 與接線規則
  • 設定入口、主題、語系與 SVG icon contract
  • 測試、瀏覽器驗收、部署與回滾證據

不在這張先做

  • 任一 App 的內容資料模型重做
  • PAYUNi、Email、GitHub kit 履約
  • 學生自訂 CSS 或任意 HTML 注入
  • 把 demo 當成正式 runtime 的第二套真相
對焦結論：先定產品骨架，再做功能。 本頁是 SR 設計對焦稿，不代表正式 app 已完成修改。
