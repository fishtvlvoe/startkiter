三種方案比較

已完成

方案一：輕量檔案慣例

現況（docs/buyer-extension-convention.md）
  • 固定資料夾／進入點格式，AI 照著寫
  • 買家要自己 git commit、重新 build/deploy
  • 要懂終端機指令、環境變數設定
  • 沒有裝解機制，改完代碼才生效
0 天已經做完，但對小白不友善
規劃中（parked）

方案二：中量級 Mount Points

platform-shell-plugin-architecture（12/45 task）
  • Core 定義路由／選單／內容／資料表四種掛載點
  • Plugin manifest 宣告掛載位置與權限
  • Marketplace 頁面列出可安裝項目
  • 裝完仍要重新 build/deploy 才生效（未打通自動化）
2–3 週剩餘 task；重建後檔案結構已變，需先重新對焦
全新工程

方案三：真 WordPress 動態載入

執行期熱插拔，不需重新部署
  • Next.js 沒有 PHP 那種原生動態載入機制
  • 要自建沙盒／動態載入引擎，技術風險高
  • 買家體感最像真的 WordPress，裝完即生效
  • 先前已評估否決過（cordis 方案），理由是不必要的不穩定依賴
6–10 週以上需另開大型 change 仔細設計，時程與風險都最高
注意：方案二的 12 個「已完成」task 是重建官方底座（rebuild-from-official-upstream）之前規劃的，當時改的 app-shell.tsx、site-nav.tsx 等檔案在重建後已經不存在，等於這部分要重新對焦，不是「剩 33 個」這麼簡單。

你描述的流程，其實是第四個方案

你講的「買家在 Codex 寫代碼 → 用我們的方式編譯 → 生成一個檔案 → 用我們的 MCP 傳送到伺服器 → 直接安裝完成」——這不是方案三（執行期動態載入），是方案二 + 一層自動化部署管線。差別在於：買家不用碰 git、不用碰終端機、不用懂 Cloudflare 怎麼設定，這些全部包進「編譯 → MCP 推送 → 自動安裝」這個黑盒子裡，但底層還是「重新建置＋部署」，不是真的執行期熱插拔。

結論與建議

建議

不要直接衝方案三（真 WordPress 執行期動態載入）。Next.js 沒有 PHP 那種天生的動態載入能力，硬做等於要自己蓋一套沙盒引擎，之前評估 cordis 時就已經否決過類似方向，理由是「一人公司的教學產品不需要背這種不穩定依賴」。這個判斷放到現在還是成立，只是規模更大、風險更高。

對純小白客群來說，「感覺像 WordPress」比「真的是 WordPress」重要。買家真正在意的不是背後有沒有執行期熱插拔，而是「我不用碰 Git、不用碰終端機、不用懂 Cloudflare，點一下就能用」。這個體感可以靠方案二（Mount Points／Manifest／Marketplace）架構 + 你描述的『編譯打包＋MCP 推送＋自動安裝』部署管線做到，而且直接沿用已經規劃好的 MCP Gateway，不是砍掉重練。

下一步：重啟 platform-shell-plugin-architecture 前，先處理它跟重建後程式碼結構對不上的落差，再把「編譯打包＋MCP 自動部署」正式寫成這張 change（或新開一張）的一部分，而不是事後補。
