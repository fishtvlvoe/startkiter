# 多課程前台銷售與交付優先

日期：2026-10-11
狀態：已決定，待施工 SR 落地

## 情境

StartKiter 現有課程、PAYUNi、訂單、課程權限、GitHub 代碼包與 LINE 邀請能力分散在不同模組。若先做完整 CRM 或電子報，會缺少最重要的可驗證商業閉環：創作者能否在公開頁面販售多門課程，買家能否付款並收到正確交付。

## 決定

第一個 end-to-end 垂直切片固定為：

```text
多門課程
  → 公開銷售頁
  → 單課 Offer／多課程 Bundle Offer
  → PAYUNi
  → Order
  → 一門或多門課程權限
  → 每門課的 LINE 邀請與歡迎信
  → 唯一 GitHub 代碼包資格
  → 交易型通知與事件紀錄
```

課程是可重用的 Content Resource；Product／Offer 決定販售方式；同一門課可被多個 Offer 引用；一個 Offer 可授予多門課程權限。公開銷售頁可以展示多門課程與各自 CTA，且頁面修訂不改寫歷史訂單。

GitHub 代碼包是全平台唯一的一種交付物，不包含課程教學內容。現有 GitHub App 仍從同一份範本為每位買家建立個人私人 repo，權限限定唯讀（pull）。買家購買多門課程時，Course entitlement 可以有多筆，但 GitHub 代碼包資格與個人 repo 只能有一份；退款只有在買家沒有其他有效代碼包資格時才撤銷 repo 存取。

## 為什麼不是先做 CRM／電子報

- CRM 與電子報需要真實的 Contact、Consent、Purchase、Entitlement 與事件資料。
- 先完成銷售與交付，後續名單與電子報直接接真實付款事件，不建立空轉資料。
- 交易型通知仍屬第一階段必要交付；行銷電子報與分眾自動化延後到第二階段。

## 替代方案

- 先做完整 CRM：否決，缺少真實購買與交付事件，無法驗證創作者最重要的商業閉環。
- 先做單一課程銷售頁：否決，會把資料模型焊死在目前單一課程，無法承接多課程與 Bundle。
- 先做完整漏斗編輯器：否決，編輯器成本高於第一階段必要價值；先做可發布的公開銷售頁與 Offer CTA。

## 後果

- 第一張施工 SR 必須同時處理多課程 catalog、公開銷售頁、CourseOffer、PAYUNi checkout、Order、課程 entitlement 與唯一代碼包資格。
- 必須先定義「頁面展示課程」與「付款後授權課程」的資料關係，避免把前台卡片直接當成訂單權限。
- CRM／電子報不是取消，而是依賴第一階段的 Contact、Consent 與 purchase events 延後施工。
